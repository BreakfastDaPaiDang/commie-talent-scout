# 1.0.0 分阶段集成与发布

S01 / #55，2026-09-30。需求继续使用 PRD 修订 1；本次讨论中的工作倾向推送留在本地 `proposal/1.0.0.1-handoff` 分支（`936a202`），不进入 1.0.0 实施范围。

## 分支和生产门控

`main` 推送会自动发布生产。1.0.0 功能分支汇入 `integration/1.0.0`，功能验证和 S11 均针对这个集成版本。`.github/workflows/release.yml` 的生产任务仅允许 `refs/heads/main`；向其他分支提交或从其他分支手动运行工作流不会发布生产。staging 使用自己的 D1/R2 与 `scripts/release.mjs --env staging`。不把未接通的原型导航挂到正式页面。

可独立进入 main 的改动：S01 的现有档案规则抽取、规则视图及测试，S10 的个性化标签说明与现有能力补缺。前提是没有更改 0.1.x 数据语义、权限、定时行为及既有页面。S01 不增加迁移：已入伙仍关闭，引荐中仍是旧状态，工作状态仍需明确关联成员。不要把包含后续功能的整条集成分支提前合入 main。

必须留在集成分支的改动：人事任务、社员身份与页面归属、引荐与入社联动、周期任务、退出联动，以及依赖这些规则的前端/MCP/定时处理。S03 开始可以增加兼容表/列，但不能提前转换正式业务数据。修改迁移文件或破坏性结构变化继续由既有 manifest 检查拒绝；不得为了通过发布检查，把不兼容迁移标为兼容。

## 可执行规则的后续接入点

- `app/shared/archive-states.ts`：当前状态策略，网页与 MCP 共用。S06 根据身份规则替换旧状态语义，并同步更新界面、协议和测试，不能只删一个状态名。
- `app/server/rules/archive-lifecycle.ts`：档案变化的命名条件、SQL 结果和执行顺序；`Archives.transition` 调用。后续增加身份／任务联动时在相应业务操作中产生同一批 SQL。
- `command()`：继续把鉴权、业务条件、事件和请求收据放在一个 D1 batch 中。自动任务的唯一业务触发键仍须由后续任务实现保证，不能用 request_id 代替月份／触发去重。
- 规则视图：`npm run rules:generate`，提交生成结果；`npm run rules:check` 和测试/CI 检查漂移。图和索引读取正在执行的规则；复杂权限、成员冻结与标签来源判断链接原函数，不伪称图已解释函数内部。

此结构只处理本次明确的档案联动；不将资料、图片、材料改为通用工作流，也不支持用户编辑规则。

## S11 与 S12 的边界

S11 在隔离环境验证完整链路、重复／并发、时区、期限、读取权限、迁移前后数量与历史引用，并演练部署失败恢复。先把旧档案和旧关联人的映射列成可复核清单；身份与唯一任务责任不能由代码猜测。正式转换脚本需要可重复执行、审计和核对模式，具体脚本随相关功能和 S11 交付。

S12 才使用已核对的真实映射执行转换并生成首批正式月度任务。上线前记录版本、备份与任务起始月，按演练顺序停用旧写入／调度、转换、部署并核对新入口。业务转换后不能直接放回不理解新数据的旧程序；数据恢复与代码回滚的界限、操作窗口在 S11 演练后固定，转换后开放写入前验证备份可恢复。现有自动发布的“失败回滚代码”不等于已经恢复业务转换。

本文件确定隔离与接入方案，不代表 S11 演练或 S12 生产迁移已完成。版本未通过完整验收前，不关闭 #54。
