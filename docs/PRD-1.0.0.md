## 1. 问题与目标

早餐社需要持续了解外部人物、外部组织与社员，沉淀资料、观察和联系情况，并让需要开展的工作有人承接、有结果可查。

原系统主要围绕外部观察和引荐设计：入社会结束档案，工作责任依附于状态，尚不能完整承载社员的持续沟通。1.0.0 延续同一份人物档案，通过身份决定页面归属，通过任务表达具体工作，通过看板让全组了解谁在做什么。

本版目标：

- 同一个人的资料、观察、材料和历史贯穿外部接触、入社、社员阶段及退出，不重复建档。
- 持续了解社员的近况、困难、需求与参与意愿，避免成员长期无人关心；工作不以凑观察条数为目的。
- 任务由本人接取，明确单人责任；做不了时容易主动交还，避免拖到失败后才被动交接。
- 系统自动生成、提醒与收尾，降低使用者维护流程的负担；人和 Agent 都能完成工作。
- 标签与观察形成能够持续修正、追溯和复用的上下文，为未来组织系统保留接入能力。

系统名称“康米巨星”与副标题“猎头系统”不变。电脑办公体验优先，手机保障基本可用性。

## 3. 使用者、社员与权限

### 3.1 概念与资格

- **系统使用者**：具有人事系统账号的人，包括普通使用者与管理员。
- **社员**：具有早餐社成员身份的人，是人物档案描述的对象；不等同于人事系统账号。
- **任务负责人**：当前正式接取任务的唯一使用者；不是档案所有者、组织大使或管理员权限的同义词。
- **组织大使**：长期联系、了解某个外部组织的内部成员，可以多人。
- **人事任务**：组内需要承接并交代结果的工作。它与现有 MCP 请求留存中的“Agent 任务／任务审阅”分别存在，不共用其短期留存或到期清理含义。

建立社员档案不要求为其注册人事系统账号。所有人事系统使用者均可查看全部未删除的外部人物、组织和社员档案，不设置社员资料专属权限分区；已删除档案、记录与受限来源继续遵守既有可见性规则。

只有社员才能获得人事系统账号是长期资格原则，未来由总人员系统提供身份依据并落实。本版沿用管理员开户，不建设自助注册或自动社员资格核验。未来绑定总系统账号不自动授予人事系统访问权，也不自动授权其他应用读取人事资料。

### 3.2 权限基线

| 操作 | 普通使用者 | 管理员 |
| --- | --- | --- |
| 查看与维护开启档案、身份与关系、需求、标签 | 可以，受既有来源与生命周期规则约束 | 可以，遵守相同规则 |
| 维护观察记录 | 自己提交的记录，编辑留史、删除可恢复 | 可以处理他人的记录，同样留史 |
| 管理词库、材料和已删除档案 | 沿用现有具体权限 | 沿用现有管理权限 |
| 手动创建、领取任务 | 可以；责任由本人接取建立 | 可以；不替别人接取 |
| 放弃负责、延期、确认完成 | 当前接取者操作自己的任务 | 自己为接取者时同样适用；不默认代替他人确认完成 |
| 取消明显无效任务、处理无人维护的异常 | 按任务角色与实施权限细则 | 可以，保留处理原因与历史 |
| 账号与权限管理 | 不可以 | 可以，保留冻结与至少一名有效管理员等保护 |

本版不设置任务协作者字段，也不建设额外的人事组资格、按任务类型接取资格或管理员审批流程。任务的普通取消、重开、评论维护等细项采用第 15 节默认值；所有入口执行相同权限。

## 4. 档案、身份与关系

### 4.1 同一份档案的连续性

人物与组织继续共用档案、观察、绑定材料、标签和历史等基础能力。档案使用稳定标识，名称可修改且允许同名；联系方式和资料链接允许多条，也允许暂时未知。

外部人物正式取得社员身份后，自动出现在社员页面，并从外部人物范围移出。已有资料、历史、链接与引用继续有效，不复制或新建第二份档案。页面归属从当前身份确定，不维护两套人物资料。

取得身份与完成入社对接是两件事：尚待对接的人也已经是社员。入社不再自动关闭档案，也不要求对象先注册人事系统账号。可为现有社员直接建档；批量导入、已有社员的对接任务处理在最终迁移时核对，不从建档推定所有人刚入社。

社员的参与工作、休假、可接新活等情况先使用现有标签表达，不新增一组固定状态字段。“沉寂”的数据化定义和专门的“当前任务”字段留待未来需求，不能把不活跃直接等同于退出或关闭。

### 4.2 外部人物与人事工作

外部人物关系保留“视奸观察”“个人接触”，新增：

> **外部社友**：对方了解组织，并与组织、工作组或项目保持相对稳定的联系或协作，但不具有社员身份。

参与独立工作组或项目不等于入社，外部社友也不以最终入社为必然目标。

旧状态中的人事工作改由任务表达：

| 业务意图 | 新版表达 |
| --- | --- |
| 引荐中，待人事组接触 | 自动创建待领取的人事审核任务，不额外创建前置“待接触”任务 |
| 人事审核 | 由审核任务表达责任与进展，档案可显示任务摘要 |
| 已加入待对接 | 确认社员身份，转入社员页面，自动创建待领取的入社对接任务 |
| 已入伙 | 用社员身份表达，不再作为自动关闭档案的状态 |

任务创建者、修改身份的人及此前档案关联人都不自动成为任务负责人。关系状态不强制线性推进；审核任务完成也不自动等于加入组织，取得社员身份须是明确业务结果或动作。

### 4.3 外部组织与大使

组织保留“视奸观察”“个人接触”“组织交流”“已弃用”。“组织交流”至少关联一名内部大使，允许多人；其他关系可保留关联成员。

大使帮助内部使用者知道联系某组织或了解其情况时先找谁。进入组织交流、指定或更换大使不自动创建交流任务；具体交流事项手动创建任务，负责人通过接取确定。

长期关联与任务责任分别展示。大使关系不会因具体任务完成而消失；切换组织关系时沿用当前按关系保留关联历史的能力，不默认把旧关系中的人任命为新任务负责人。组织月度观察由独立周期规则生成，不把它混同为切换到“组织交流”的副作用。

### 4.4 关闭、退出与重新开启

关闭档案表示停止观察与维护，内容和历史保留且可查看。关闭后基础资料、需求、标签、材料和观察不能继续维护，须显式重新开启；删除与恢复等生命周期操作继续按现有权限执行。

| 动作 | 页面与关系 | 开关 |
| --- | --- | --- |
| 正式入社 | 社员页面 | 保持开启 |
| 社员转为社友 | 外部人物，外部社友 | 保持开启 |
| 社员直接退出组织 | 外部人物的已关闭范围 | 自动关闭 |
| 外部人物／组织设为已弃用 | 原对象范围 | 自动关闭 |
| 社员休假、沉寂、暂不接工作 | 仍是社员，可用标签记录 | 不自动关闭 |

每次身份变化、关闭和重新开启均保留操作人与时间。直接退出事实留在历史中，不推定为外部社友。重新开启不等于恢复社员身份，也不批量重开旧任务。

档案身份变化与账号访问是不同问题。本版尚未建设总系统身份绑定，不能宣称关闭人物档案就自动冻结其账号；账号处理沿用现有管理能力。

## 5. 观察、标签与长期上下文

### 5.1 观察与历史

观察记录支持短记事、长文与图片，不强制标题。原作者和管理员按既有权限维护，编辑留版本、删除可恢复；来源与图片权限、关闭锁定继续生效。

历史线同时呈现观察和系统事件，观察正文保持视觉重点。实际资料变化留史，无变化重复保存不制造活动；系统事件不自动变成观察记录。草稿、图片、长文阅读和已读行为继续保持。

社员观察不必来自实际接触：作品、动态等有用情况同样可以留档。观察者未来可以是人、AI 或系统；观察来源、提交身份与实际沟通者不能混为一谈。当前 Agent 仍在授权账号身份下操作，不新增无人值守观察或行为采集。

### 5.2 标签兼容个性化特征

保留标签定义、档案绑定、绑定依据三层结构，以及人物／组织分库、类别、重点展示、定义版本、合并、停用、删除恢复与关闭快照能力。社员与外部人物共用人物标签库，入社不丢失或另复制标签。

标签可以只适用于一个对象，多人复用不是创建门槛。不另设“档案要点”；优先查找含义合适的已有标签，但不为复用牺牲表达准确性。公共描述解释词义，具体对象的态度、适用范围和判断原因写在绑定依据中。

例如对某类内容的偏好不能直接推导对某类人的协作意愿，标签不是自动录用或排除指令。它可以更新、移除和追溯，不是永久定性或人员评分。

### 5.3 面向未来的可利用性

观察保留事实与背景，标签和依据提炼当前值得记住的特征。保留稳定标识、引用、来源种类、版本、确认时间和权限，让有权使用的 Agent 能检索并回查。

新材料没提旧标签或需求，不表示它失效。来源于观察的依据继续受来源权限保护，不能通过摘要、标签或未来索引绕过删除和访问限制。

未来索引、向量和临时摘要应能由保留的资料重新生成，资料不依赖某个模型或 Agent 的私有记忆。1.0.0 保留这些结构，不建设向量库、推荐引擎、独立资产平台或自动画像更新流程。

## 6. 通用任务机制

### 6.1 任务表达

每项任务至少表达以下信息，系统可填写默认值并隐藏内部维护细节：

| 信息 | 用途 |
| --- | --- |
| 标题 | 一眼知道要处理什么 |
| 任务描述 | 为什么做、希望了解或解决什么、本次工作背景和具体要求 |
| 交付要求 | 工作结果写在哪里、如何交代；不以机械格式代替目的 |
| 关联档案、任务类型、可选所属月份 | 找到工作对象，辨认周期与生成原因 |
| 当前开关与负责人 | 是否继续处理、当前由谁承接 |
| 当前期限 | 待领取时是接取期限，接取后是完成期限 |
| 关闭结果与历史 | 本次结局、历次接取、放弃、延期与重开经过 |
| 评论、结果引用 | 过程协作，以及档案中已沉淀的交付 |

常态界面主要呈现目的、交付要求、当前责任、期限及需要执行的动作，不展示实现、存储或排错说明。

### 6.2 开关与责任

任务只有开启／关闭这一生命周期维度；开启且无负责人表示待领取，开启且有负责人表示已接取。关闭结果分别为完成、过期未接取、未完成、取消。

所有使用者可手动创建任务并领取待领取任务。创建不自动分配，不直接替别人建立责任；接取后只有一名负责人。不记录协作者名单，不要求维护额外的“等待回复”等进度状态。

“放弃任务”是鼓励主动交还工作的正常操作：解除当前负责人，保持开启，回到待领取，并确定新的接取期限。原承接与放弃过程留史，不记失败。不强迫负责人拖到失败或等别人追问才交接。

### 6.3 期限与自动收尾

所有开启任务必须有明确期限，包括重新开启、放弃回到待领取后的任务。系统可以按任务类型提供默认值；具体天数留到实施时确定。

- 接取期限到达仍无人领取：自动关闭，记录“过期未接取”。
- 已接取任务在完成期限前提醒负责人；到期未完成则自动关闭，记录“未完成”。
- 不设置额外宽限期，不等待用户回复提醒后才结束，也不靠某人打开 Agent 才运行到期处理。
- 当前负责人可主动延期，期限变化留史；查看、已读和普通评论均不自动延期。
- 自动清理是结束当前工作并保留历史，不是删除任务，不把失败或无人接取记成完成。

定时执行、读取和写入必须对期限含义保持一致；调度延迟不能形成业务宽限。过期后要继续做，应明确重新开启及新期限。提交结果、延期和到期关闭并发时，不能产生两个有效结果或静默丢失人工操作。

### 6.4 完成与交付

当前完成权属于接取者，不要求管理员普遍审批。部分任务可以绑定明确的自动完成条件，在相关业务操作满足条件时完成，省去再次进入任务页或单独调用 MCP 完成工具的步骤。

自动完成是便利路径，不排除接取者直接确认完成。任意观察、评论或档案更新不能无条件完成任务；应明确对应哪项任务与其条件。自动条件不从自由文本自行猜测，也不自动完成别人的任务。

月度社员沟通不强制已经收到回复、发生实际交流或提交一条新观察才能点击完成。接取者可据实完成，包括已经尝试但目前联系不到；工作要求仍是在关联档案留下结果，不在任务评论重复提交。没有交代而拖到期，与已如实跟进并确认完成分别处理。

未来可支持由管理员审批完成的任务，当前不实现审批界面或多阶段审批流；内部设计避免把完成权限散落到调用者中即可。

### 6.5 评论、历史与重新开启

评论记录进展、困难与说明；系统历史记录创建、领取、放弃、期限调整、提醒、结果关联、关闭和重开。观察成果引用原档案记录，不复制成另一份交付正文。

关闭后只读，补充评论须重新开启。重开表示恢复工作，必须明确是否保留原负责人并确定新的期限；不得自动把别人重新任命为负责人。之前的关闭结果留在历史，再次关闭登记本次结果，不抹掉失败，也不无条件沿用以前的完成结果。

失败后原接取者仍可以重新开启继续做。普通取消、评论维护与管理异常的细项采用第 15 节的默认规则。任务的可读内容和结果引用始终受档案、来源及账号权限约束。

### 6.6 周期独立性

上月与下月是不同任务，各自有责任、期限、交付与结果。上月任务未结束不阻止生成下月任务，允许补作业和多次联系，不限制为同一对象同类工作仅一项开启任务。

同一对象、任务类型、月份的重复生成须去重，手动和自动生成复用此规则。不同月份不合并、不自动抵扣；提交结果需能指向具体任务。是否已有一条观察不直接代表当月沟通完成。

## 7. 人事任务与自动化业务规则

### 7.1 任务类型与目的

人事规则决定为什么产生任务、对应哪个档案、满足什么业务条件；通用任务模块负责接取、期限和生命周期。以下是产品要求，不另手工维护一份与代码同步的执行规则表。

| 类型 | 产生方式 | 工作目的与结果去向 |
| --- | --- | --- |
| 人事审核 | 明确进入待人事组接触／引荐时自动生成，初始待领取 | 了解对方情况与意愿，形成可继续处理的审核结论；结果沉淀在人物档案 |
| 入社对接 | 正式取得社员身份、需要入社对接时自动生成，初始待领取 | 帮助新社员了解组织与后续联系安排，留下对接结果及待关注事项 |
| 社员月度沟通 | 每月按纳入范围的社员档案生成 | 持续了解、支持和保持联系，具体要求见 7.2 |
| 外部人物／组织月度观察 | 每月为未关闭、未删除的外部人物和组织档案生成 | 了解近期变化、联系与需求，把有用结果写入档案；无适用资料时如实交代，不为凑条数编造 |
| 具体交流或其他人事事项 | 使用者手动创建 | 创建者在描述中说明目的，交付要求明确结果所在位置 |

月度生成以组织使用的东八区自然月为口径，从上线确定的起始月份开始，不自动补建旧月份。已存在的社员先纳入档案，才能参与生成；不能根据人事系统账号名单假定它等于全体社员名单。

接取期限、完成期限及提醒时间可按类型不同。重复保存身份或重复定时执行不重复创建同一业务事项的任务；新的再次引荐或再次入社不能被永久去重规则阻止，按明确的新业务发生处理。

### 7.2 月度社员沟通模板

**任务描述**：了解该社员近期的生活与参与情况，看看是否遇到困难、需要支持，或有想参与、调整的事情。结合已有联系自然交流，不必逐项询问，也不要求对方当月必须参与工作。若暂时联系不到，如实留下情况，供后续跟进。

**交付要求**：将本次跟进结果及需要后续关注的事项写入关联社员档案的观察记录；未能取得联系时，也在档案中如实说明。无需在任务评论中重复提交结果。

上述是工作要求，不作为“没有新观察或实际交流就不能点击完成”的系统硬校验。任务描述说明目的，交付要求说明留档位置；不强制字数、问卷或逐项询问。

本版不增加任务完成与实际沟通成功的统计拆分，也不将结果自动用于 KPI 考核。

### 7.3 对象变化的联动

- 明确正式入社时转入社员页面并生成对接任务。若相应审核任务交付已完成且结果被确认，可按明确规则完成审核；仅改身份不能推定所有审核要求均已满足。
- 社员转为社友或直接退出：取消尚未结束的社员月度沟通和入社对接任务，注明身份变化；已完成、失败及其他结束历史保留。
- 档案关闭：取消依赖继续观察或维护该档案的开启任务，并记录原因。
- 档案重新开启：不批量复活旧任务；按当前需要重开具体任务或生成新的周期任务。
- 手动交流、合作任务不因人物身份变化一律取消。向负责人提示，由其继续、延期或取消，原期限有效。
- 指定组织大使或收集“当前需求”不自动产生任务。

因不再适用而取消，区别于负责人到期未完成。后来的身份变化不能改写过去的失败历史。任务结果也不自动决定对方已入社、已弃用或应该恢复身份。

## 8. 当前需求与联系方式

### 8.1 当前需求

外部人物、组织、社员档案均增加自由文本“当前需求”，允许多项内容和留空。它收集对象需要什么，不表示组织承诺解决，不自动创建任务。决定跟进时可以手动创建关联任务。

网页和 MCP 可读写；档案详情直接返回该字段。服务端 Agent 指引明确要求整理材料时主动识别明确表达的需求，在既有授权范围内记录或更新；没有依据则建议或询问，不编造。

更新前读取现有需求，保留本次未涉及的内容；只有明确依据或指令才移除已解决或不再需要的需求。旧客户端不传字段不能清空已有值。写入沿用权限、版本、历史与关闭锁定。

### 8.2 多种联系方式提醒

提醒范围是社员（包括尚待入社对接者）、外部社友，以及处于“个人接触”或“组织交流”的组织。

少于两条不同的可用联系方式时提示补充。同一地址或账号重复填写不算两条，不强制跨平台；不新增自动拨测或真实性认证。

网页展示提醒，MCP 修改相关档案后的成功结果返回同样提醒，方便 Agent 继续提示。提醒不阻止保存，不将成功写入报告为失败；达到要求后停止。具体去重和避免重复催促的方式在实施时处理。

## 9. 页面与主要交互

### 9.1 导航与称呼

左上主导航为：**外部人物｜组织｜社员｜任务｜统计**。

原人物入口及相关列表称呼统一为外部人物；“人物档案”仍用于外部人物与社员共有概念。标签库移至右上账号菜单。右上铃铛进入消息提醒页，所有使用者可见；猎头管理齿轮仍仅管理员可见。辅助工具与 Agent 接入保留，名称、副标题和既有文案语气不整体改造，不新增帮助入口。

手机导航具体表现实施时确定，但上述入口及基本操作可达；不为手机投入与电脑同等规模的专项设计。

### 9.2 档案页面

外部人物、组织和社员采用共用界面能力，保留搜索、筛选、记录、标签、材料、阅读和编辑体验。社员页面突出当前情况与关联沟通工作，可帮助找到本月仍待处理的成员；不能仅以是否新增观察推定任务已完成。

档案可展示关联人事任务的摘要和入口。组织长期大使与具体任务负责人区分，不能用任务责任覆盖长期联系资料。“当前需求”与联系方式提醒融入正常资料维护，不增加技术说明墙。

关闭档案保持可读且结束状态清楚；入社不再显示代表档案结束的旧“已入伙”处理。既有链接、搜索和已读能力在身份切换后仍能定位同一档案。

### 9.3 任务看板

任务页是了解全组工作状态与开展协作的看板，不只是接取列表。应让使用者容易回答：有哪些工作待领取、谁正在负责、什么快到期、最近交付了什么、哪些工作无人领取或未完成。

全组任务及失败结果对系统使用者可见，受引用来源权限约束。当前待办不被大量已结束任务淹没，但结果和历史可查。按自己／全组、类型、周期和结果查看的具体布局由前端设计确定，不把看板等同于必须可拖拽的列式流程。

任务详情突出目的、交付要求、关联对象、责任与期限，提供接取、放弃、延期、完成和按权限取消／重开。放弃入口清楚、正常，不以惩罚语气阻碍主动交还。评论与系统历史在同一工作上下文展示，关联观察可回到档案阅读。

### 9.4 消息提醒

原未读更新页升级为消息提醒页，保留档案更新与既有阅读确认。新任务由使用者主动从看板领取，不向全体逐条通知；周期生成也不产生全员通知。

本版先做好公共页面和后端能力，接入负责人临近到期提醒，以及 7.3 所需的对象变化提示。任务评论等通知类型后续按需要添加，不把所有事件都转成消息；无人接取和失败主要在看板查看。

读取消息不等于接取、完成或延期。档案摘要已读也不能替代原有内容阅读要求，升级应保持既有个人阅读标记和按权限确认机制。

### 9.5 设计与验收顺序

开做任务看板时，先使用生图模型生成视觉意向稿，提炼布局和视觉灵感，再形成可操作的界面方案。生图不是精确业务原型，也不代替交互验证。

正式页面继续基于已确认共享界面，原型和正式站引用同一套界面模块。设计变更先说明，修改后对照历史原型并验证真实接口；完整编辑表单、发布区、任务详情与手机操作分别验收。电脑体验优先不等于手机无法完成基本操作。

## 10. MCP 与 Agent

新业务通过 MCP 提供与网页一致的权限和结果：身份与关系维护、任务查询和详情、创建／接取／放弃／延期／完成／取消／重新开启、评论与历史、消息读取，以及当前需求维护。具体工具名称与请求形式在技术设计阶段确定。

服务端业务指引须同步新版语义，尤其说明：

- 社员档案不等于登录账号，入社延续档案且不关闭；外部社友不具有社员身份。
- 任务责任只能通过本人接取建立，创建任务和组织大使不等于负责；做不了可主动放弃。
- 工作结果写入关联档案，评论用于过程协作；联系不到可如实交代并由接取者完成。
- 标签不要求多人复用；需求应主动识别、据实记录；新材料未提及不等于清空旧资料。
- 多联系方式不足时，根据操作结果提醒使用者；已有明确授权时执行，不添加重复许可流程。

指引由 MCP 服务按需返回，不仅依赖首次提示词。既有读取版本、授权、图文、重试、来源保护与未读确认继续生效。新增人事任务标识与原 Agent 调用上下文标识分开，不把一次工具调用当成人事任务完成。

自动完成和周期处理仍由服务器规则执行，不依赖 Agent 永久记住提示词；Agent 可协助人维护任务，但不获得独立超级权限。

## 11. 架构与实施约束

### 11.1 可执行规则与生成视图

采用 [ADR 0014](./adr/0014-executable-business-rules.md)：身份、档案生命周期与任务联动集中在可执行定义中，触发条件与结果容易找到，规则索引和流程视图从实际参与执行的定义生成。不额外手工维护第二份规则表，不只从注释生成一张可能与实现脱节的图。

复杂判断可引用有明确名称的函数，视图给出源码入口，不宣称可以完整解释任意代码。PRD 维护目的与验收要求，代码是具体联动实现来源；两者职责不同。

局部重构仅覆盖身份与档案生命周期、人事任务生成和周期规则等相关逻辑，不要求把普通资料编辑、图片等全部改造成规则框架，不引入通用工作流平台或用户自定义规则引擎。

### 11.2 一致性与可替换性

继续采用 [ADR 0003](./adr/0003-shared-worker-business-layer.md) 的共享业务层，网页与 MCP 调用相同业务操作；复用权限、版本检查、事务、历史及重试机制。由业务生成任务时需业务级去重，不仅检查请求重试标识；相关身份变化与任务联动不能只成功一半。

通用任务模块与人事规则分开。未来组织统一任务系统可以承接通用标识、领取、责任、期限、进度和历史，人事系统保留规则与工作入口。负责人和状态届时只保留一个权威来源，不长期双向同步两套任务。

消息类型复用统一接收、存储、已读与展示能力；各类触发仍属于相应业务规则。未来总系统与独立业务仓库如何拆分不作为本版建设前提。

## 12. 用户故事

以下覆盖本版新增与保留的关键路径，按故事编号供实施 Issue 引用。

### 档案与身份

1. 作为系统使用者，我希望从外部人物、组织、社员入口找到对象，以便按当前工作场景查看资料。
2. 作为记录者，我希望人物入社后沿用原档案，以便此前观察、材料、标签和历史继续可用。
3. 作为人事使用者，我希望直接为已有社员建档且无需创建账号，以便先建立完整社员名册。
4. 作为接触者，我希望把稳定协作但不入社的人标为外部社友，以便准确表达关系而不催进入社流程。
5. 作为使用者，我希望看到组织的长期大使，以便知道找谁了解或联系该组织。
6. 作为人事使用者，我希望入社立即改变页面归属并产生待领取的对接任务，以便身份和未完工作分别清楚。
7. 作为人事使用者，我希望转为社友时继续维护同一档案，以便保留联系与协作。
8. 作为人事使用者，我希望直接退出时把原档案放入外部已关闭范围，以便保留过去资料而停止维护。
9. 作为使用者，我希望休假或沉寂仍能用标签和观察记录，以便不把临时情况误作退出。
10. 作为管理员，我希望新身份与任务功能遵守现有冻结、删除及来源权限，以便功能扩展不绕过访问约束。

### 信息沉淀

11. 作为记录者，我希望留存非接触类观察，以便作品或动态等信息不被排除。
12. 作为记录者，我希望观察、图片和材料继续支持编辑留史与恢复，以便资料持续积累且可以纠正。
13. 作为使用者，我希望创建仅适用于一个人的标签，以便准确表达有协作价值的个性化特征。
14. 作为阅读者，我希望区分标签含义与该对象的具体依据，以便理解判断的范围与来处。
15. 作为维护者，我希望入社前后复用同一人物词库，以便不重复建设或丢失标签。
16. 作为授权 Agent，我希望按需读取记录、标签、依据与历史，以便用完整背景辅助工作。
17. 作为记录者，我希望维护当前需求，以便后续协作知道对象需要什么而不暗示组织已承诺。
18. 作为使用者，我希望 Agent 整理材料时主动留意需求，以便有价值的明确需求不会遗漏。
19. 作为资料维护者，我希望收到补充多种联系方式的轻量提示，以便稳定联系且不被阻止保存。

### 任务协作

20. 作为使用者，我希望创建任务时说明目的与交付位置，以便接取者知道为什么做和如何交代。
21. 作为使用者，我希望先看全组看板再主动领取，以便选择适合自己的工作。
22. 作为接取者，我希望任务只有一个当前负责人，以便责任明确。
23. 作为接取者，我希望做不了时容易放弃并交回待领取，以便别人及时承接而非等到失败。
24. 作为接取者，我希望系统提供合理期限且可以主动延期，以便安排工作而不维护复杂状态。
25. 作为接取者，我希望在到期前收到提醒，以便决定交付、延期或放弃。
26. 作为全组使用者，我希望无人接取或到期未完成的任务自动结束并留史，以便待办不无限堆积。
27. 作为接取者，我希望自行确认完成，以便一般工作无需管理员审批。
28. 作为接取者，我希望符合明确条件的交付可以自动完成关联任务，以便省去重复操作。
29. 作为沟通任务接取者，我希望联系不到时仍能据实完成，以便任务反映真实跟进而非强求对方回复。
30. 作为记录者，我希望成果写在档案并由任务引用，以便不用在评论再复制一份。
31. 作为协作者，我希望用评论说明进展或阻碍，以便大家了解过程。
32. 作为使用者，我希望看到领取、放弃、延期、关闭和重开历史，以便理解责任与结果变化。
33. 作为原接取者，我希望失败后能够明确新期限并重开，以便继续补做且不抹去原结果。
34. 作为管理员，我希望取消无效任务和处理异常，以便工作空间可维护且不变成普遍审批。
35. 作为使用者，我希望关闭任务保持只读，以便结束结果不被悄悄追加或改写。

### 人事规则与周期工作

36. 作为引荐者，我希望待人事组接触时自动产生审核任务，以便工作被正式领取。
37. 作为新社员对接者，我希望入社时产生独立对接任务，以便未完成的对接不会因身份已改变而遗漏。
38. 作为人事使用者，我希望每月有社员沟通任务，以便持续了解成员的情况和需要。
39. 作为观察者，我希望开启的外部人物与组织每月有观察任务，以便持续关注有用变化。
40. 作为接取者，我希望各月份任务独立，以便上月欠缺可以补做而不阻止本月工作。
41. 作为使用者，我希望重复生成同月份任务不会产生副本，以便领取与责任不重复。
42. 作为接取者，我希望对象退出或档案关闭后，无意义的周期和对接任务自动取消，以便不继续做已失效的工作。
43. 作为合作任务负责人，我希望身份变化后由我判断合作是否继续，以便有效事项不被一律取消。
44. 作为组织大使，我希望长期联系关系不强制产生具体交流任务，以便有实际事项时再任务化。

### 消息、Agent 与维护

45. 作为使用者，我希望消息页同时承载已有档案更新和必要任务提醒，以便集中查看需关注的变化。
46. 作为使用者，我希望新任务主要在看板主动领取，以便月初生成不会刷满个人消息。
47. 作为使用者，我希望读消息不会自动完成、接取或延期，以便阅读与业务决定分开。
48. 作为授权 Agent，我希望通过 MCP 完成与网页一致的任务操作，以便使用者不必来回切换入口。
49. 作为维护者，我希望人事任务与 Agent 调用审阅分别处理，以便审阅数据到期清理不会删除工作历史。
50. 作为开发者或 AI，我希望从集中可执行定义查明业务联动并生成视图，以便减少漏改和重复实现。
51. 作为未来组织系统维护者，我希望通用任务能力可替换而人事规则保留，以便接入总系统时不用重写人事业务。
52. 作为使用者，我希望任务看板既清楚又便于长时间使用，以便了解组内协作而非只操作零散按钮。
53. 作为手机使用者，我希望仍可阅读、领取、写结果和处理任务，以便临时操作不被设备限制。
54. 作为上线维护者，我希望业务迁移最后执行且能核对恢复，以便现有资料和责任不被误转换。
55. 作为上线维护者，我希望提前生成指定月份的任务，以便九月上线后可以准备十月工作且不会重复生成。
56. 作为使用者，我希望当前统计和已交付辅助功能继续可用，以便新版不强加自动考核或破坏已有工作。

## 13. 验收与验证

### 13.1 验证方式

以使用者可观察的业务结果为准，不以数据字段存在、生成图成功或某个按钮出现替代完整验证。优先通过现有共享业务操作这一验证入口，配合网页与 MCP 的契约检查；复用现有档案、权限、图文、标签、阅读和回滚验证方式。

周期与到期规则使用可控时间验证，无需真实等一个月。真实网页／MCP 链路在隔离测试环境用虚构数据验证，并清理测试产物；公开证据不含真实人物、内部材料或凭据。设计验证保留历史原型对照及真实接口操作，完整表单、发布区、失败与手机状态分别检查。

以下为本版必须覆盖的验收场景，不表示测试已经执行：

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A01 | 导航与角色 | 顺序和称呼正确；标签库在账号菜单；所有使用者可见铃铛，只有管理员有猎头管理 |
| A02 | 人物入社 | 同一稳定档案、内容与链接连续；进入社员范围；不关闭；仅创建对应的一项待领取对接任务 |
| A03 | 社员直接建档 | 无需创建登录账号，资料可维护；不把已存在社员误判为刚入社 |
| A04 | 转为社友／退出 | 前者外部开启、后者外部关闭；历史与数据保留，不自动变更账号资格 |
| A05 | 组织大使 | 支持多人，长期关系保留；切换组织交流不自动生成交流任务 |
| A06 | 个性化标签 | 仅一个对象也能创建与绑定；入社不丢标签；定义、依据、历史及来源权限保持 |
| A07 | 观察与来源 | 非接触观察可保存；原作者权限、图文版本、恢复、材料与关闭锁定继续有效 |
| A08 | 需求维护 | 网页与 MCP 一致；详情带字段；省略字段不清空；服务指引主动识别且不自动建任务 |
| A09 | 联系方式提醒 | 指定对象少于两条不同联系方式才提示；重复账号不充数；成功写入仍返回成功 |
| A10 | 创建与领取 | 创建不分配；两人并发领取只有一名负责人，另一人收到可理解的冲突结果 |
| A11 | 放弃任务 | 解除本人责任、保持开启、返回待领取且有接取期限，保留历史不记失败 |
| A12 | 延期与评论 | 明确延期更新期限并留史；浏览、已读或评论不延期；旧期限提醒不错误生效 |
| A13 | 无人接取到期 | 自动关闭为过期未接取，不删除；重复检查不重复产生关闭结果 |
| A14 | 已接取到期 | 提前提醒；到期即未完成，无宽限；调度延迟不允许过期任务被当作正常开启任务完成 |
| A15 | 并发收尾 | 完成／延期／到期处理结果一致、留史、不重复任务和消息，不出现一半成功 |
| A16 | 人工完成 | 由接取者完成；月度沟通联系不到仍可据实完成，不被观察数量或回复条件拦截 |
| A17 | 自动完成 | 只有明确匹配当前任务、责任与条件的操作才触发；普通观察不误完成别的月份或他人任务 |
| A18 | 关闭后补充与重开 | 关闭只读；重开明确责任和新期限；旧结果保留，再关产生本次结果 |
| A19 | 周期独立 | 十月未完成不阻止十一月生成；两个任务分别领取、交付与收尾 |
| A20 | 同周期去重 | 手动、定时、重试和并发生成同月不产生重复；再次入社等新事项仍能生成新任务 |
| A21 | 人事联动 | 引荐产生审核任务；退社取消不适用工作；取消不算失败；重开档案不批量重开旧任务 |
| A22 | 手动事项 | 身份变化不盲目取消有效合作；负责人得到提示，可继续、延期或取消 |
| A23 | 看板完整性 | 全组能查看待领取、在做及结束结果；失败可查；放弃入口清楚；交付回到档案 |
| A24 | 消息与未读 | 旧档案阅读标记保持；到期消息面向负责人；新任务不广播；已读不改变业务责任 |
| A25 | 网页／MCP 一致 | 任务与档案操作拥有同一权限、状态、结果与重试语义；冻结或越权调用被拒绝 |
| A26 | 来源与删除权限 | 任务搜索、评论引用、消息摘要和结果链接不能绕过已删除档案或受限观察权限 |
| A27 | 规则可发现性 | 视图由实际执行定义生成，变更可追踪；业务行为测试独立证明结果，不能仅对图做快照 |
| A28 | 既有 Agent 审阅 | 原调用关联与留存照常；人事任务不会随请求留存到期被删除 |
| A29 | 完整界面 | 历史原型对照、真实接口、任务全过程、完整编辑发布与手机操作均验证，不以样式相等替代 |
| A30 | 指定月份首批任务 | 九月生成十月任务按十月期限，月初再次运行不重复；不默认补建九月 |
| A31 | 迁移与恢复 | 预览目标和结果；稳定标识、历史不丢；多负责人不随意选人；重复执行可控，失败可恢复 |
| A32 | 现有能力回归 | 统计界面、辅助工具、DSH 引导、凭据与材料等继续可用，不新增自动考核 |

## 14. 交付顺序与最终迁移

实施 Issue 按可验收业务路径拆分，具体技术依赖在拆分时确定。建议先建立共享规则与身份能力，再打通任务及人事规则、MCP、看板和消息，完成综合验证后执行最后的数据迁移与上线核对。前端开做前按 9.5 先探索意向稿。

**最后一项实施 Issue 必须是旧档案业务迁移与上线数据核对**，依赖相关功能完成。当前确有一份引荐中档案需要转换，执行时在私有环境按稳定标识核对，不把真实人物信息写进公开 Issue。

旧状态、社员资格与责任应按实际数据列出转换预览。此前提出的所有旧状态映射和自动沿用旧负责人都不是批量执行授权；尤其旧档案有多个关联人时，不能任意选一名作为新任务接取者。迁移应保留档案、观察、材料和历史，并可核验、重复执行及恢复。

必要数据库结构、旧入口兼容和代码部署顺序须先在技术方案处理。“迁移最后”不表示允许新代码先在不兼容旧数据上运行。账号权限、旧 MCP 状态工具和原档案链接均需有明确兼容或清楚拒绝与引导策略，不能静默套用旧语义。

首次周期支持手动指定月份批量生成，复用正常生成规则。从 2026 年 10 月准备工作，不默认补九月；若上线时机改变，由最终上线清单选择起始月。提前创建与所属月份分开，十月任务不因九月创建而在九月到期。

首次生成以核对后的社员与其他适用档案清单为准。重复手动生成、月初自动生成与恢复补跑不重复创建同一月份任务；后续月份独立。

## 15. 实施时确定的细节与开发默认值

这些不阻塞本轮 PRD 完成。实施 Issue 应记录最终选择；只有变化达到 P0/P1 才重新讨论。

| 项目 | 当前开发默认方向／约束 |
| --- | --- |
| 日期参数 | 各类任务接取、完成期限及提前提醒时间在实施时定；东八区自然月、无宽限、允许主动延期不变 |
| 周期范围变化 | 同月新增适用对象可按同一规则补生成；暂停、退出、删除不生成不适用工作；不回溯所有历史月份 |
| 自动完成具体条件 | 在各任务类型的实施 Issue 中列清触发、关联和责任条件，并至少验证实际业务路径；不开放用户编写任意表达式 |
| 任务交付模板 | 月度社员沟通采用 7.2；其他类型参照“目的写描述、成果进档案”的原则编写可调整模板 |
| 普通取消权限 | 默认负责人可取消自己的任务，创建者可取消自己创建且尚未接取的任务；管理员处理其他无效或异常任务，均留史 |
| 重新开启 | 默认原接取者可自行继续，管理员可重开为待领取；其他人需要本人接取，不能替别人恢复负责关系 |
| 直接交接 | 本版默认放弃后由下一人接取，不增加强制指派或独立交接审批 |
| 评论维护 | 默认开启时作者可改自己的评论、管理员可处理其他评论，留史、删除可恢复；关闭任务保持只读 |
| 任务内容调整 | 默认创建者和当前负责人可维护，管理员可纠正；已接取任务的要求变动须显式留史，不悄悄替换既有交付定义 |
| 账号冻结与异常任务 | 延续冻结禁止操作，任务保留历史；管理员可解除不可工作的负责人并回到待领取，不让冻结账号继续执行 |
| 退出显示与旧关联 | 退出事实明确保留；关闭卡片具体称谓、长期关联展示及旧状态映射在实施／迁移中核对，不改写历史 |
| 档案删除与恢复 | 默认停止相关自动任务并保留管理可核对结果，受限内容从普通任务与消息查询隐藏；恢复不批量复活任务 |
| 未领取手动任务的对象变化 | 默认在任务上标示变化供接取前核对，不向全员广播；有关权限仍按来源执行 |
| 消息呈现 | 铃铛计数、分类、期限变更后的旧提醒处理与单条已读形式在前端／后端设计时确定；不扩大档案既有已读范围 |
| 旧更新提醒 | 保留不冲突的现有档案提醒；已取消旧人事状态的 7 天提醒随任务期限承接，不维护两套矛盾工作进度 |
| 手动周期生成 | 默认由管理员或受控维护入口触发，先预览月份与对象；具体界面或 MCP 形式实施时确定 |

## 16. 本版不做

- 组织总人员／用户系统、统一任务平台、单点登录、自动身份核验与完整跨应用迁移。
- 人事系统内置通用 Agent、无人值守观察、用户行为采集、向量库、推荐引擎及全自动画像更新。
- 可视化工作流编辑器、用户可编程规则、复杂审批、多人负责人或协作者管理。
- 自动 KPI／API 考核、达标催交、绩效排名或处罚；统计界面改版。
- 当前需求的独立生命周期、需求自动任务化、社员自助提交需求、固定的当前工作字段或沉寂算法。
- 全员新任务广播、站外推送、复杂通知订阅及大规模手机专项设计。
- 系统名称、副标题、整体术语语气改版或新增帮助入口。
