# 非人类执行主体与常驻 Agent（未来方向）

2026-10-09 讨论确认：后台自动化与未来常驻人事 Agent 不应借用某个真实社员的 MCP 凭据，也不应简单伪装成一个拥有全部管理员权限的机器社员。未来系统需要支持非人类执行主体，并区分固定系统规则与 Agent 自主执行。

这不是 1.0.0 的实施范围。本文记录已确认的方向，供后续身份、MCP 和任务系统设计使用。

## 方向

系统可以拥有一个长期服务主体，未来常驻 Agent 可以使用该服务主体接入；但每次执行仍要记录执行方式：

- `system`：后端固定规则、定时处理或事务联动直接执行；
- `agent`：Agent 根据档案、观察、当前需求和任务上下文自主执行；
- `member`：真实社员通过网页或 MCP 执行。

服务主体不是普通社员，不出现在社员列表，不能登录、领取任务或接收个人消息。它也不自动拥有完整管理员能力。系统规则和 Agent 只获得明确列出的能力范围，所有写入继续经过现有权限、版本、事务、历史和重试保护。

## 审计要求

未来每次非人类操作至少应能追溯到：

- 服务主体；
- 执行方式（`system` 或 `agent`）；
- 固定规则编号、Agent 会话或调用上下文；
- 触发来源，例如定时、状态变化、人工调用或 Agent 判断；
- 产生的任务、档案变化、消息和历史。

不要求 Agent 写入必须绑定某个社员授权人。未来 Agent 可以自主读取、分析、创建和维护任务；责任边界由服务主体、执行方式、能力范围和调用上下文表达。涉及状态切换、任务完成或档案写入时，仍必须走对应业务操作，不能绕过领域校验。

## 任务来源

未来任务不应把所有来源压缩进 `manual` / `rule` 一个字段。应分别记录创建主体和触发方式，例如：

- 创建主体：`member`、`system`、`agent`；
- 触发方式：手动、定时、状态变化、Agent 判断等。

Agent 创建的任务与人工、系统规则任务共用同一任务生命周期和看板。规则性 Agent 任务需要业务义务键防止周期或状态触发重复；自由任务的去重策略留待后续设计。

## 非目标

- 1.0.0 不实现常驻 Agent 管理界面；
- 1.0.0 不实现通用 Agent 工作流或用户可配置权限引擎；
- 1.0.0 不创建机器管理员成员作为后台自动化的替身；
- 本 ADR 不决定未来总人员系统的账号注册方式。
