# 0016：统一消息读取模型，保留来源的确认协议

日期：2026-10-12。状态：采纳。关联：[#73](https://github.com/BreakfastDaPaiDang/commie-talent-scout/issues/73)。延续 ADR 0006、0012 的内容阅读保证。

## 问题

消息中心虽然已经收束为一个入口，任务提醒与档案更新仍分别实现查询、计数和前端读取，扩展消息来源需要重复维护。原任务查询还遗漏了新的 `task_overdue` 类型；状态变化产生的旧 32 位消息 ID 也不能通过只接受 UUID 的确认接口。

## 决策

`NotificationQuery` 是唯一的消息查询边界，通过 SQL 投影合并任务提醒和档案事件。在过滤权限、接收人、有效性和已读条件后统一排序与分页，不先从两侧各取一页再拼接。

公共消息结构包含：命名空间 ID（`task:原ID` / `archive:事件ID`）、来源、原 ID、接收人、事件种类、发生时间、已读时间、确认方式及来源元数据。档案事件对每个接收人形成个人消息视图，并不因此复制事件正文。

网页、铃铛与 MCP 使用相同服务：

- `GET /api/notifications` / `list_notifications`：统一时间线，支持来源及未读筛选。
- `GET /api/notifications/summary` / `get_notification_summary`：同一可见性和有效性口径的总数与分类数量。
- `POST /api/notifications/confirm` / `confirm_notifications`：明确确认方式，分派到原子确认操作。

快照固定两类来源的序号上界；按时间和命名空间 ID 进行游标分页，同一时间的消息不会重复或丢失。后续新增记录留到刷新；权限与已读状态仍实时复核。快照不是正文版本快照，不冻结来源当前内容。旧档案队列保留按事件序号翻页的兼容输出，但从同一个投影查询。

## 确认不是统一的“已读=true”写入

- 任务提醒：只能确认本人当前可见且仍有效的 `task:` 消息；重复确认保留首次已读时间，不改任务状态、期限和负责人。兼容 UUID 与历史 32 位 ID。
- MCP 档案阅读：必须使用实际返回完整内容时签发的事件票据，继续校验连接、接收人、期限及观察版本。
- 网页档案阅读：必须使用本次打开签发的整档快照票据，继续限制当时可见的事件集合、复核权限并保留未读例外。
- 列表摘要和原始 `archive:` 消息 ID 不能确认正文阅读。

任务逾期提醒只在任务仍开启、期限仍匹配且已到期、负责人及任务版本仍匹配时生效。延期、交还、关闭后旧提醒失效。原已过期关闭历史提醒的兼容解释仍保留。

## 存储和兼容

本次不合并物理表。`messages.read_at` 与 `event_read_marks` 分别是各自来源的唯一已读事实，统一模型直接读取它们，不增加双写、复制消息表或迁移猜测。档案事件已有权限、长期历史和短期票据；任务提醒已有接收人、期限版本与失效规则，强行塞进同一张表不会消除这些差异。

旧 HTTP 和 MCP 名称保留为兼容适配器，不再维护另一套列表／计数条件；已存在数据立即由公共模型承接，无需批量回填或删除。回退代码无需恢复数据。本次不操作正式环境数据，也不把任务提醒的失效等同于清理档案历史。

界面继续使用现有两个来源页签和共享档案详情；这次完成数据接口收束，不重做已确认布局。

## #88：统一界面与显式全部已读（2026-10-12）

用户要求将两类消息合成一个列表，并提供「全部标为已读」。前端按统一查询时间线分页，保留来源标签，复用既有档案和任务入口。消息详情选择写入 URL；关闭和浏览器返回恢复列表，前进可恢复详情。直接进入旧 `/unread`、`/messages?tab=updates` 也展示同一个列表。

新增 `confirm_notifications` / `/notifications/confirm` 的 `mode=all`，必须带列表 snapshot。这是用户主动清除未读的操作，不声称实际阅读全文，独立于原有内容票据协议。同一事务复核当前账号/凭证、来源权限和快照上界，再写入两个原有已读存储；覆盖未加载分页，保留快照之后新增、当前隐藏或不属于本人的消息。不修改任务、档案内容和活动时间。MCP 仅在用户明确要求全部已读时使用。原有 message/event/archive 确认保持。
