# 兼容性迁移、代码回退与隔离数据恢复

正式数据与 staging 数据使用独立 D1 和私有 R2。公开仓库只保存程序、迁移、资源标识和脱敏验收结论，备份、图片、账号密钥与原始客户端记录不进入仓库或 GitHub Actions artifacts。

发布先校验迁移清单，再完成数据库快照与所有被历史版本、草稿或头像引用的图片备份，随后迁移、部署和冒烟。`migrations/manifest.json` 记录按 LF 归一化的 SHA-256 与兼容性说明；已发布迁移不可变。破坏旧代码兼容性的迁移须另行设计分阶段发布，不能通过当前自动流程。

部署开始后的失败恢复已知的前一个 Worker 版本；不自动恢复数据库。这样不会删除发布期间已经提交的业务材料。迁移失败保留原代码，需检查 D1 已执行的迁移后再重试。首次部署没有可回退代码时如实报错。

数据恢复只写入明确配置、为空且不与任何运行环境重叠的 `cts-restore-*` 数据库与图片桶。对每张表做规范化内容哈希核对，对每个图片对象核对字节哈希；随后执行与生产相同的请求记录清理，再允许考虑挂载服务。脚本不会自动替换生产绑定。

数据库快照保留 30 天，图片内容块按 SHA-256 去重，暂不自动清除，避免仍被保留快照或业务历史引用的图片误删。备份清单最后写入，表示该快照的数据库与引用图片全部备份成功。日常任务与发布共用串行锁；本地应避免和运行中的 CI 同时操作生产。

发布记录中的快照、代码版本和迁移哈希存放在私有备份桶中。恢复涉及真实数据切换时，维护者须先完成隔离核对并明确切换目标，不把代码回退等同于数据回退。
