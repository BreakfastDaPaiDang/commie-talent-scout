# 康米巨星猎头系统 PRD

版本：v1.0（产品基线）

日期：2026-09-08

状态：核心产品规则已对齐，其余产品细节按用户授权采用开发默认值；进入技术设计与实施验证准备。

## 1. 问题与目标

早餐社需要一个内部协作网页，沉淀值得关注的人物与组织的信息、观察记录和接触进度。人物档案中的多数对象，是未来可能加入组织的人。

系统应让成员快速了解：对象是谁、当前进度如何、谁正在负责、最近发生了什么、此前记录了什么。多人持续维护同一份档案，避免信息分散和重复接触。

产品暂定正式名称为“康米巨星猎头系统”。“插眼”是团队日常表达，产品中的主要数据概念采用“档案”“观察记录”“实体历史线”。

## 2. 需求确认程度

- **已确认**：用户明确提出，或在对齐中明确认可的规则。
- **开发默认值**：依照用户授权确定的产品或交互设计，作为首版实施依据，可以根据实际使用反馈调整。
- **技术待验证**：由开发者研究、设计和实测的事项，尚未完成验证；只有发现会改变核心范围、权限、成本或访问要求的取舍时，才重新与用户对齐。

本版本保留的“建议”措辞均表示可调整的开发默认值，不表示等待用户逐项批准。

对齐约定：仅向用户讨论 P0/P1 事项。P0 指阻止核心闭环成立或影响基本访问权限的问题；P1 指显著影响日常协作、内容处理、首版范围或接入可用性的问题。其余可逆细节由开发者采用合理默认值并记录，不逐项要求用户确认。已确认规则优先于默认值。

已确认的核心范围包括：人物和组织档案、各自的业务状态、多负责人、图文观察记录、实体历史线、关闭与重新开启、成员协作权限、记录修改留史、管理员账号管理、账号密码登录、MCP、复制 Agent 配置提示词、公开代码仓库与数据分离、优先 Cloudflare serverless 和 GitHub 更新自动部署、所有页面的视觉品质。

未读更新是用户期望功能，首版纳入简单未读列表与逐条跳转。如果实施中发现会显著影响核心交付，再说明具体取舍，不预先删减。

## 3. 用户与权限

系统只有管理员和普通成员两类用户。无自助注册。

| 操作 | 普通成员 | 管理员 |
| --- | --- | --- |
| 查看全部人物和组织档案 | 可以 | 可以 |
| 创建档案 | 可以 | 可以 |
| 修改开启中档案的基础资料、状态、负责人 | 可以 | 可以 |
| 给开启中的档案添加观察记录 | 可以 | 可以 |
| 修改开启中档案里自己提交的观察记录 | 可以，保留修改历史 | 可以，保留修改历史 |
| 修改开启中档案里他人提交的观察记录 | 不可以 | 可以，保留修改历史 |
| 删除开启中档案的观察记录 | 仅自己的记录，可恢复删除 | 任意记录，可恢复删除 |
| 恢复开启中档案的已删除观察记录 | 仅自己的记录 | 任意记录 |
| 关闭和重新开启档案 | 可以 | 可以 |
| 修改关闭档案内的内容 | 不可以，必须先重新开启 | 不可以，必须先重新开启 |
| 创建、冻结账号、授予管理员权限 | 不可以 | 可以，通过管理后台 |

观察记录采用可恢复删除：作者只能删除和恢复自己的记录，管理员可以删除和恢复任意记录。作者归属不因管理员编辑或删除而改变。此权限不包含永久清除记录或删除整个档案。

账号管理采用以下开发默认值：

- 账号冻结立即阻止登录及后续网页、MCP 请求，并使现有会话和个人 MCP 凭证失效；已有内容与作者归属保留。
- 管理员可以解冻账号、将管理员降为普通成员、重置密码。解冻后须重新登录并重新生成已失效的 MCP 凭证；降权立即影响后续操作权限。
- 成员可修改自己的密码。管理员创建账号或重置密码后提供临时密码，首次使用需更换；不引入邮件找回流程。
- 系统始终保留至少一名未冻结的管理员，拒绝会破坏该条件的冻结或降权操作。
- 首位管理员通过一次性初始化方式建立，具体机制在技术设计中落实，初始凭证不进入仓库。
- 账号管理动作保留操作者和时间，供管理员追溯；第一版不提供永久删除账号。

## 4. 档案与业务状态

### 4.1 共同结构

人物与组织是两种实体，分别提供入口，共用档案、观察记录、历史线、协作权限和生命周期规则。

共同信息：稳定标识、实体类型、显示名称、业务状态、开启或关闭状态、状态负责人、创建人、创建时间、最近内容更新时间、观察记录、实体历史线。

人物以昵称、组织以名称作为必填识别字段；联系方式允许暂时未知。开发默认值：两类档案均支持可多条填写的联系方式（类型、值、备注）、可选别名、简介和资料链接；创建时仅要求昵称或名称及有效业务状态，业务状态默认“视奸观察”。

名称不强制唯一；创建前可检索并提示相似名称，避免同名不同对象无法建档。第一版不提供自动身份归并或档案合并。

### 4.2 人物状态

| 状态 | 负责人关联 | 开关规则 |
| --- | --- | --- |
| 视奸观察 | 未指定专属负责人字段 | 开启 |
| 个人接触 | 接触用户，可多选、可变更 | 开启 |
| 引荐中（待人事组接触） | 接触用户，可多选、可变更 | 开启 |
| 人事审核 | 审核负责用户，可多选、可变更 | 开启 |
| 已加入待对接 | 对接负责用户，可多选、可变更 | 开启 |
| 已入伙 | 保留既有负责人历史 | 自动关闭 |
| 已弃用 | 保留既有负责人历史 | 自动关闭 |

### 4.3 组织状态

| 状态 | 负责人关联 | 开关规则 |
| --- | --- | --- |
| 视奸观察 | 未指定专属负责人字段 | 开启 |
| 个人接触 | 接触用户，可多选、可变更 | 开启 |
| 组织交流 | 接触用户，可多选、可变更 | 开启 |
| 已弃用 | 保留既有负责人历史 | 自动关闭 |

**已确认：业务状态没有先后顺序。** 开启中的档案可以自由切换到该实体类型的任一合法业务状态，不要求经过其他状态或按某种顺序操作；切换到关闭类状态时自动关闭。系统记录状态变化，不建立流程顺序或前置状态限制。关闭后的修改仍受关闭锁定规则约束。

负责人采用开发默认值：允许暂未分配，支持多选、增减与替换；只能新分配未冻结的成员，既有被冻结负责人保留并显示冻结标记。各状态的负责人分别保留，切换状态不会清空其他状态的关联。开启档案可展开维护非当前状态的负责人，每次变更进入历史线；此前的历史事件不被改写。

### 4.4 关闭与重新开启

**已确认的业务含义：关闭就是停止观察，包括不再观察或对象失联；想继续观察，必须重新开启。**

- 不允许出现“仍在持续观察，但档案暂时关闭”的业务状态。
- 关闭后，基础资料、业务状态、负责人、观察记录和图片内容都不能修改，也不能新增、删除或恢复观察记录。
- 关闭档案仍可查看，历史内容保留。
- 重新开启是关闭状态下允许的生命周期操作；普通成员和管理员均可执行。
- 进入人物“已入伙／已弃用”、组织“已弃用”时自动关闭。
- 每次关闭和重新开启均生成明确的历史事件，包含操作人和时间。
- 业务状态变化同时触发关闭时，两件事都须清楚呈现，不遗漏“已关闭”的历史信息。

**已确认的关闭表达**：“已弃用”统一涵盖失联、不再在乎或其他不再关注的情况，不新增“已失联”状态，也不设置独立的关闭原因字段。需要详细说明时，成员在关闭前补充一条普通观察记录；说明不是关闭的必填条件。

关闭档案的当前展示突出“已入伙／已弃用”和“已关闭”，此前的业务状态保留在历史中。重新开启时选择一个有效的开启类业务状态；选择与开启一并完成。默认值采用关闭前最后一个开启类状态，没有该状态时采用“视奸观察”；成员可自行更换。此默认值是可逆的交互选择，不表达状态顺序。

## 5. 观察记录与实体历史线

### 5.1 观察记录

- 每个档案可以绑定多条观察记录，支持文字和图片，兼容短记事与较长文章。
- 显示提交用户、创建时间和最后修改时间。开发默认值：允许另填观察发生时间用于补录，未填写时按提交时间理解；补录时间不改变档案最近内容活动排序。
- 普通成员只能修改自己提交的观察记录，管理员可以修改全部记录。
- 每次编辑保留历史版本及修改人、修改时间；不覆盖成无法追溯的唯一版本。
- 记录采用可恢复删除：从普通列表中隐藏内容，保留记录、历史版本及关联图片，能够恢复。
- 作者只能删除和恢复自己提交的记录；管理员可以删除和恢复任意记录。权限依据原始作者判断，而不是删除人或最后修改人。
- 删除和恢复均写入实体历史线，记录操作人和时间；恢复保留原始记录标识、作者、创建时间与历史版本，不创建一条新记录。
- 档案关闭期间，即使作者或管理员也不能编辑、删除或恢复观察记录；必须先重新开启。

建议：图片修改同样进入版本历史，历史版本能够呈现当时的图文内容。图片数量、大小和保留策略在技术设计阶段确定。

开发默认值：图文编辑支持直接粘贴或选择多张图片，正文与图片至少有一项；无强制文章标题。已删除记录从普通列表隐藏，在“已删除记录”入口查看和按权限恢复，原有全员查看档案的范围不变。删除记录不是保密或永久清除操作。

### 5.2 实体历史线

历史线不仅是观察记录列表，还自动包含业务状态变化、已关闭、已开启及发生时间。建议同时记录档案创建、基础资料变更、负责人调整、记录编辑等事件，并显示操作人。

对需要追溯的字段变更，建议展示变更前后值。用户不能直接编辑系统生成的历史事件。

**观察记录必须是历史线的视觉重点，不能被操作事件淹没。**

建议交互：

- 观察记录采用更大的内容卡片，直接呈现正文摘要和图片缩略图。
- 系统事件采用紧凑行，不给每次操作相同的视觉重量。
- 提供“全部动态”和“仅观察记录”切换。
- 默认按最新在前排列；长正文按需展开，图片可以放大查看。
- 记录编辑事件链接到对应记录和版本差异，避免把同一篇长文重复堆进时间线。

## 6. 页面与主要交互

### 6.1 登录

简单账号密码表单，无注册入口。登录错误、账号被冻结、会话失效等状态给出清楚反馈。

### 6.2 人物与组织列表

已确认：按档案最近内容变动排序，最近有变动的在前；观察记录变化同样影响排序。人物卡片下方罗列观察记录供查看，组织页面采用类似体验。

建议：

- 提供人物／组织切换，以及名称搜索、状态、负责人、开启／关闭筛选。
- 卡片展示名称、状态、负责人、最近更新时间和最近几条观察记录。
- 更多记录在档案详情内连续查看，避免首页加载全部长文与图片。
- 新建、编辑、删除和恢复记录，修改资料、变更状态或负责人、关闭／开启都会更新内容活动时间；无实际内容变化的重复保存不产生新动态。
- 单纯查看、标记已读不影响档案排序。
- 默认展示开启中的档案，提供明确的已关闭和全部档案筛选。

### 6.3 档案详情与记录编辑

建议桌面端以宽侧栏呈现详情，上方为基础资料和状态操作，下方为实体历史线，直接在其中添加或编辑观察记录。

长内容可展开到更大的阅读空间，并为档案和记录提供独立链接。移动端采用全屏详情，以适应小屏幕。无需为了写一句观察笔记跳转到独立文章创作页。

关闭档案明确显示只读状态和重新开启入口。修改入口的界面限制与服务端权限检查保持一致。

### 6.4 未读更新

用户希望逐条查看上次没看过的状态更新和观察记录，并直接跳转到相应内容。

第一版提供未读列表、定位原记录／事件、下一条未读、全部标为已读。已读状态按用户独立保存。

开发默认值：

- 打开对应内容时标为已读；首页卡片出现不自动算已读。
- 自己通过网页或 MCP 产生的操作不进入自己的未读列表。
- 他人新增、编辑、删除、恢复观察记录，以及修改档案资料、负责人、业务状态、关闭或开启，形成新的未读动态；已读旧版本不代表读过新修改。
- 删除动态显示删除提示，不能通过未读摘要把已删除正文重新放回普通列表。
- 新账号从账号创建后的更新开始接收未读，既有档案仍可主动浏览；自己的已读操作不影响别人。
- 首版不做邮件、站外推送或在线聊天通知。

### 6.5 账号后台

管理员可查看账号列表、创建账号、冻结账号、授予管理员权限。普通成员不显示后台入口，直接访问或通过 MCP 调用也必须被权限校验拒绝。

### 6.6 Agent 接入页

提供 MCP 接入说明、当前用户的连接配置方式，以及“一键复制提示词”。提示词初稿见 [Agent 接入提示词](./agent-onboarding-prompt.md)，供用户继续调整；实际地址、认证步骤和工具名称随实现补齐。

已确认：首版使用 Codex 验证接入和完整业务操作。复制内容应包含 MCP 服务地址、认证配置指引、系统用途和操作规则，方便成员交给自己的 Agent 完成配置并开始使用。其他客户端的接入细节由开发者处理，不作为逐项需求对齐事项。

建议将通用使用说明与个人凭证分开呈现；提供凭证创建和撤销能力，复制结果明确说明用户接下来需要做什么。

### 6.7 视觉要求

已确认：所有页面都要有审美，包括登录、后台、详情、空列表、错误反馈和接入说明。

建议采用适合长时间阅读的内部资料工具风格：清晰的字体层级、克制的状态色、稳定的间距、足够宽的正文区域、舒适的图片预览。人物与组织保持统一设计语言，记录内容优先于装饰。

视觉采用开发默认值：深墨色文字、暖白背景和克制的暗红强调色，以资料阅读和快速记录为重点；状态同时使用文字与颜色。桌面采用宽侧栏，手机采用全屏详情，核心操作均可完成。具体设计通过可操作原型检验，不为配色、字号等可逆细节另开需求访谈。

## 7. MCP 与 Agent 行为

### 7.1 能力范围

已确认：Agent 通过 MCP 可以执行对应用户能够执行的全部业务操作，而不只是查询。

范围包括档案查询与创建、资料修改、状态和负责人变更、关闭和开启、观察记录查询与图文提交、按权限编辑、删除和恢复记录、查看历史、读取和标记未读更新，以及当前成员有权执行的账号管理与个人账号操作。

### 7.2 身份与规则

建议网页与 MCP 共用同一套业务规则和权限检查。每个 MCP 操作归属于一个已认证的成员账号，并记录来源；Agent 不获得独立的超级权限。

关闭档案的限制、作者编辑／删除／恢复限制、管理员限制，同样适用于 MCP。冻结账号后，其 MCP 操作也应失效。

### 7.3 图片

图片应纳入 Agent 创建观察记录的正式能力。建议流程是先上传图片并获得附件标识，再在提交观察记录时引用附件。Agent 本机文件路径不能直接作为其他成员可浏览的图片地址。

具体采用 MCP 上传工具、短期上传地址或其他协议，在技术验证中确定。需要验证网页、MCP 客户端、附件存储与历史版本之间的完整路径。

首版以 Codex 实测“配置接入 → 上传图片 → 创建图文观察记录 → 网页查看”的完整路径，并验证与网页一致的查询、编辑、删除、恢复、关闭、开启及管理员权限。实现完成前，以上属于验收目标，不表示已经完成兼容性验证。

### 7.4 提示词的预期内容

- 系统用途、人物与组织的区别。
- 状态含义、负责人规则、关闭与重新开启规则。
- 在创建档案前检索已有对象，降低重复建档。
- 如何组织观察记录、提交图片、引用资料来源。
- 区分原始信息、观察者判断和不确定内容，避免 Agent 将推测写成既成事实。
- 修改权限、操作归属，以及遇到权限不足或档案关闭时的处理方式。
- 查询与写入的示例任务、连接配置步骤。

上述内容已形成 [可审阅初稿](./agent-onboarding-prompt.md)。技术配置占位符在接口落实后补齐，提示词不能替代服务端权限检查。

## 8. 用户故事

1. 作为成员，我希望用管理员发给我的账号密码登录，以访问内部资料。

4. 作为成员，我希望创建组织档案，以持续记录组织相关信息。
5. 作为成员，我希望最近变动的档案排在前面，以优先了解最新进展。

11. 作为成员，我希望快速提交短文字或图文长记录，以适应不同观察材料。

17. 作为成员，我希望关闭后的内容锁定，以保留停止观察时的档案状态。
18. 作为成员，我希望重新开启档案后恢复维护，以继续此前停止的观察。
19. 作为成员，我希望历史线显示开启、关闭及状态变化，以还原完整经过。
20. 作为成员，我希望观察记录比系统事件更醒目，并可单独筛选，以专注阅读材料。
21. 作为成员，我希望逐条查看未读更新并跳转原处，以补齐上次访问后的信息。
22. 作为管理员，我希望创建和冻结账号，以控制内部访问资格。
23. 作为管理员，我希望授予其他账号管理员权限，以共同管理系统。
24. 作为成员，我希望复制清楚的接入提示词，以让自己的 Agent 理解并使用系统。
25. 作为成员，我希望 Agent 能按我的权限读写档案和提交图片，以减少手工搬运。

## 9. 实施方向与约束

仓库已有 PRD、项目说明、Matt 开发流程配置及领域词汇表，尚无应用代码、既有接口或测试可复用。领域术语见根目录的 [CONTEXT.md](../CONTEXT.md)；重要架构取舍明确后再写入 [决策记录](./adr/)，普通产品规则直接维护在本 PRD。

已确认的部署方向：

- GitHub 公开仓库：`BreakfastDaPaiDang/commie-talent-scout`；网页产品名称保留“康米巨星猎头系统”。
- 真实业务数据不能存入仓库；图片、账号数据、凭证等也应与源码分离。
- 优先采用 Cloudflare serverless 服务。
- 已确认的上线要求：中国大陆成员无需使用代理即可正常访问网页并完成核心操作。
- GitHub 更新后自动部署。开发默认值：main 分支通过必要检查后部署生产环境，开发分支不覆盖生产；测试使用独立数据，部署回退不得通过清空真实数据实现。具体连接方式、迁移顺序与回退操作在技术设计中落实。

域名与访问方案：用户已提供自有域名 dapaidang.org，已通过现有本机 Wrangler 授权调用 Cloudflare API，确认该域名位于可访问账号下且 zone 状态为 active。正式入口默认拟用 scout.dapaidang.org，部署时先检查子域名占用，再绑定项目；当前尚未修改 DNS 或部署应用。

若采用 Workers Custom Domain，在有效的 Cloudflare zone 中绑定域名时，Cloudflare 可自动建立对应 DNS 记录并签发证书，见 [官方自定义域名文档](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)。DNS 配置完成只说明域名接入完成，不代表大陆网络可用性已经验收。本次账号连接检查通过环境现有代理完成，不作为大陆无代理访问验证。

上线前需在成员实际使用的大陆无代理网络中验证登录、列表、记录读写、图片上传和查看；覆盖可获得的不同运营商网络并记录测试条件和结果。Cloudflare 官方说明跨境访问存在延迟和可靠性问题，见 [China Network 概述](https://developers.cloudflare.com/china-network/)。Cloudflare 是优先方案，实际访问结果决定是否满足上线要求；若不满足，调整部署方案后重新验证。尚未部署，尚无实际网络验证结果。

开发默认值：字体、脚本和核心界面资源随应用提供，避免核心操作依赖额外的公共资源域名。MCP 的验收仍使用成员实际运行 Codex 的环境，不把网页无需代理的要求扩大为第三方 Agent 服务本身的网络承诺。

建议的职责划分：账号与鉴权、档案与状态规则、观察记录与附件、历史与未读、网页界面、MCP 入口。网页和 MCP 调用同一业务层，避免规则分叉；不预先拆为多个独立服务。

数据库、附件存储、前端框架、MCP 传输与认证方式、数据库迁移与部署顺序，将在技术方案阶段验证和决定。本产品基线不将任何云产品能力视为已经验证。

内部访问边界同时覆盖网页、业务接口、MCP 和图片附件；公开源码或知道一个图片地址不赋予读取权限。图片存储与传输方案须维持这一边界，具体机制在技术设计中落实。

## 10. 验收与验证方案

建议主要在已认证的业务接口边界验证可观察行为，另用少量网页与 MCP 端到端场景验证入口可用性。当前没有既有测试先例；具体测试边界待技术设计时确认。

| 验收场景 | 预期行为 |
| --- | --- |
| 普通成员修改他人的观察记录 | 网页和 MCP 均拒绝，原内容不变 |
| 作者或管理员修改开启档案的记录 | 更新成功，旧版本及修改人、时间可追溯 |
| 普通成员删除或恢复他人的观察记录 | 网页和 MCP 均拒绝，即使该成员曾参与相关档案维护 |
| 作者删除或恢复自己的记录，管理员删除或恢复任意记录 | 开启档案中操作成功；保留原始作者、内容版本与关联图片，历史记录操作人和时间 |
| 管理员编辑或删除了一条记录，原始作者恢复该记录 | 在档案开启时允许恢复；作者权限不因管理员操作而转移 |
| 关闭档案中的记录被尝试删除或恢复 | 包括作者和管理员在内，网页和 MCP 均拒绝 |
| 档案已关闭，任何成员尝试修改或新增内容 | 网页与 MCP 均拒绝；必须先重新开启 |
| 成员将开启档案切换到该实体类型的任一合法业务状态 | 不检查前置状态或顺序；记录变化，目标为关闭类状态时同时关闭 |
| 人物进入已入伙或已弃用，组织进入已弃用 | 业务状态更新与关闭一起完成，历史明确包含两种变化 |
| 成员因失联或不再关注而弃用档案 | 统一使用已弃用并关闭，不要求单独填写关闭原因；需要说明时可在关闭前提交普通观察记录 |
| 成员重新开启档案 | 恢复可维护状态，历史包含已开启事件和时间 |
| 多名负责人被新增、替换或移除 | 当前关联正确，历史保留前后变化 |
| 档案新增或编辑观察记录 | 档案按新的活动时间参与列表排序 |
| 成员只查看档案或标记已读 | 档案活动时间和排序不因此改变 |
| 时间线包含大量系统事件 | 观察记录仍醒目，且可只查看观察记录 |
| Codex 完成 MCP 接入并创建含图片的观察记录 | 按页面复制说明完成接入；网页中可正常查看提交的文字和图片，作者与操作来源正确 |
| 管理员冻结账号 | 阻止该账号后续网页与 MCP 访问，已有会话与凭证失效，历史作者归属保留 |
| 普通成员直接调用管理员操作 | 服务端拒绝，不依赖是否隐藏按钮 |
| 未登录访问档案、记录、历史版本或附件地址 | 不能读取内部内容；网页、业务接口与 MCP 的访问规则一致 |
| 成员 A 阅读更新 | 不能改变成员 B 的已读状态；旧记录的新修改产生新的未读动态 |
| 冻结或降权操作将导致没有未冻结的管理员 | 拒绝操作，账号和角色保持原状 |
| 公开仓库与部署检查 | 仓库中无真实业务资料、图片、账号凭证；部署能访问独立数据存储 |
| 中国大陆成员使用正式域名、在不使用代理的网络中访问网页 | 能登录、浏览和维护档案、上传及查看图片；记录实际运营商与测试结果，DNS 生效不能替代业务操作验证 |

视觉验收应覆盖登录、列表、详情、编辑、关闭档案、后台、接入页，以及加载、空白和错误状态；检查长文本、多图、窄屏下的阅读与操作体验。

以上作为首版验收依据；实现方案变化时同步更新相关用例，但不能在未说明的情况下降低已确认要求。

## 11. 范围边界

已明确不包含自助注册，公开仓库不意味着档案对外公开。

建议第一版暂不包含：自动抓取外部平台、自动识别人脸或关联身份、自动给人物评分或决定招录、复杂组织层级和逐档案访问控制、对外消息发送、复杂审批流、实时协同编辑。用户当前未请求这些能力。

第一版不提供永久清除观察记录、删除整个档案或账号。误建档案可补充说明后设为已弃用；观察记录按已确认权限可恢复删除。

简单未读功能纳入首版；如需因具体实施成本调整范围，再向用户说明取舍。

## 12. 对齐结论与技术验证

目前没有必须再次向用户提问的 P0/P1 产品规则。状态、权限、记录删除和恢复、MCP 验证目标、大陆访问要求均已明确，其余产品默认值已写入对应章节。

进入技术设计后由开发者完成：

1. 确定应用、数据库、私有附件存储、鉴权和 MCP 的实现方式，确认所需 Cloudflare 权限、资源限制及费用；涉及实际购买或显著预算取舍时提供具体方案。
2. 用 Codex 验证接入、图文写入与权限一致性，补齐提示词中的配置步骤和工具名称。
3. 检查 scout.dapaidang.org 占用并落实正式域名绑定，实测大陆无代理网络的完整访问路径；现有账号连接成功不能替代该项。
4. 通过界面原型验证长记录、多图片、历史事件密集和手机使用时的体验。
5. 明确数据备份与恢复方式、自动部署检查、数据迁移和回退步骤，真实数据始终与公开仓库分离。

本 PRD 是产品基线，不代表应用已实现、技术验证已通过或部署已完成。后续按 Matt 流程形成技术方案，并将能够独立实施的工作拆成 GitHub Issues。
